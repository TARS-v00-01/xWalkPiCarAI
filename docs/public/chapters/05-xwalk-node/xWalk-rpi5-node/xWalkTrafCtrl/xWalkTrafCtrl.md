# xWalkTrafCtrl

`xWalkTrafCtrl` is a native C++17 traffic-announcement application. It captures local video or Raspberry Pi 5
CSI frames, runs the trained crosswalk detector and Random Forest, validates IW Protobuf observations,
generates bounded LLM advisories, and publishes them as the existing IW `SoundReq` with operation `ANNOUNCE`.
Capture, configuration, model inference, Protobuf observations, LLM calls and tests are native C++; there is no
Python application, subprocess inference, Python Protobuf binding or Python test bridge.

## 1. Overview

The executable composes static libraries that each own one stage of the pipeline. Announcements are traced
through the `TRAFCTRL` trace module. The receiving node stores and speaks each advisory with its existing sound
handler. `xWalkTrafCtrl` is a separate executable and service: it links the reusable MQTT transport libraries
but does not launch the IoT executable, its queues, IPC endpoints, command subscriptions or controller
workers. Start and stop the two applications independently; they share only the intended MQTT topics.

The application has three operating paths:

- **Host replay** evaluates a local video, still image, JSON report or Protobuf observation offline.
- **Raspberry Pi live capture** consumes the CSI camera (directly or through
  [xWalkCameraSvc](xWalkCameraSvc/xWalkCameraSvc.md)) and runs the independent
  [front proximity monitor](xWalkProximity/xWalkProximity.md).
- **Safety IPC commands** (`--proximity-status`, `--all-stop`) query or latch the hardware owner's proximity
  stop and exit without loading models.

This model estimates crosswalk proximity risk with a fixed image-relative crosswalk rectangle. It does not
detect crashes or traffic-light states. The prompt cannot guarantee factual generated wording. Never
interpret SAFE as permission to cross.

## 5. Public interface

The executable's command-line contract is defined by
`xWalkTrafficHelp.json`, which is
copied to `<build>/config/` and installed to `share/xwalk/help`. Use `--help` to list native options.

| Option | Purpose |
| --- | --- |
| `--build-mode` | Print the compiled backend (`host` or `rpi5`) and exit |
| `--config FILE` | Merge a partial deployment configuration |
| `--host`, `--rpi5` | Require the matching compiled backend; omitted means the build mode |
| `--video FILE` (`--vedio`), `--image FILE` | Host local video or still image |
| `--report FILE`, `--protobuf-input FILE` | Replay a JSON report or Protobuf observation without model files |
| `--weights`, `--rf-model`, `--model-root`, `--input-size`, `--device`, `--confidence` | Model settings |
| `--llm-endpoint`, `--llm-model`, `--llm-timeout-ms` | LLM provider settings |
| `--camera-pipeline`, `--frame-stride`, `--max-frames`, `--announcement-interval` | Capture and pacing |
| `--evaluation-output FILE` | Write one JSONL prediction per processed frame |
| `--trace SELECTOR` | Repeatable; explicit selectors replace configured selectors |
| `--proximity-status`, `--all-stop` | Safety IPC query or latched stop request, then exit |

`--proximity-status` and `--all-stop` print `clearance_mm`, `valid`, `latched`, `stop_succeeded` and
`threshold_mm`. They exit with status 2 when the IPC is unavailable, or when `--all-stop` is not latched and
acknowledged. An unhandled provider failure terminates the application with exit status 2.

`TRAFCTRL.001` reports accepted observations, `.002` reports a skipped SAFE result, `.003` prints
announcements and `.004` reports the selected host detector backend. Module warning and error macros remain
unfiltered. Trace settings control logging only; they do not disable LLM generation or MQTT delivery.

from the build alongside the executable; trace logs go into its `log` directory. Copy the tracked configuration
directory with the executable and retain target-local overrides and credentials separately.

### Native host dependency setup

The exported trained YOLO graph fails in OpenCV 4.6 even when synthetic tensor tests pass. Non-Hailo builds
require OpenCV 4.10 or newer; the deployment model is verified with 4.12.0. Python's `opencv-python` package does
not provide the C++ dependency. Build the pinned native dependency in an isolated prefix as described in
[xWalkTrafCtrl Host Dependencies](cmake/host-dependencies/xWalkTrafCtrl%20Host%20Dependencies.md). The main
build discovers `build-dependencies/opencv`; `-UOpenCV_DIR` clears an older cached system selection and an
explicit `-DOpenCV_DIR=/path/to/lib/cmake/opencv4` takes precedence.

### Raspberry Pi 5 Hailo-8 detector

Hailo is opt-in and defaults to OFF. CMake selects the native implementation sources; there is no Hailo
preprocessor flag in shared model code. Both choices keep Pi CSI or shared-camera capture.

```bash
cmake --preset rpi5 -DXWALK_TRAFCTRL_ENABLE_HAILO=OFF
```

OFF uses the trained `best.onnx` and forest JSON with native OpenCV CPU inference. `device=auto` becomes `cpu`;
an explicit `hailo8`, `cuda` or `opencl` request is rejected for this Pi build. OpenCV 4.10 or newer is required
because 4.6 cannot import the trained graph; the isolated OpenCV recipe also applies to Pi CPU builds. No
HailoRT package, driver, service or chip is accessed in this mode. For a Pi deployment without the app
repository, copy the trained `best.onnx` and `crosswalk-safety.json` into `xWalkInput/xWalkModel/` and select the
supplied CPU configuration:

```bash
./build-rpi5/xWalkTrafCtrl --rpi5 --config xWalkConfig/xWalkRpi5Cpu.conf
```

```bash
cmake --preset rpi5 -DXWALK_TRAFCTRL_ENABLE_HAILO=ON
```

ON requires the HailoRT 4.23 C++ development package, matching driver and firmware, the HailoRT service, a
Hailo-8 chip and a trained `best.hef`. The switch only selects the C++ backend; it does not install or load the
kernel driver. Enabling it on a host build is a configuration error. `model.device: "auto"` resolves to
`hailo8`. There is no ONNX or CPU fallback after a Hailo failure: missing hardware, HailoRT service, incompatible
HEF or inference failure stops the run with a TRAFCTRL error. Changing the option requires rebuilding; the runtime
`--rpi5` flag continues to select Pi capture. The Random Forest remains native C++ on the CPU and the LLM still
runs through the configured Ollama endpoint. HEF compilation and output requirements are documented in
[xWalkModel](xWalkModel/xWalkModel.md).

## 7. Configuration

Run `./build-host/xWalkTrafCtrl` without `--config`:
`xWalkTrafCtrl.conf` loads
automatically. Precedence is defaults, then the host test profile (host builds only), then `--config FILE`, then
CLI overrides. Configured relative paths resolve against their containing JSON file; CLI paths resolve against the
working directory. Unknown fields and invalid types or ranges are rejected. `--image`, `--report` or
`--protobuf-input` replaces a configured host video. File inputs are rejected in Pi mode; Pi mode uses the existing
`libcamerasrc` NV12-to-BGR GStreamer pipeline. No fallback source opens silently. Changing configuration does not
require rebuilding. Complete section defaults are documented in [xWalkConfig](xWalkConfig/xWalkConfig.md).

| Section | Settings |
| --- | --- |
| `host` | `video`, optional `evaluation_output` |
| `rpi5` | `camera_pipeline`, optional `evaluation_output`, local speech settings |
| `model` | `model_root`, `weights`, `rf_model`, `device`, `confidence`, `input_size` |
| `llm` | `llm_endpoint`, `llm_model`, `llm_timeout_ms` |
| `runtime` | `frame_stride`, `max_frames`, `announcement_interval` |
| `trace` | Ordered `trace` selector array |
| `mqtt` | `enabled`, `client_address`, `server_ip`, `mailbox`, `local_index`, `module_type` |
| `hailo` | `group_id`, `multi_process_service`, `timeout_ms` |

The retired Python configuration's `backend` field and `XWALK_PYTHON` launcher variable no longer apply. LLM
defaults are `http://127.0.0.1:11434/api/chat` and `llama3.2:3b`. The advisory deadline includes cold model
loading and defaults to 180 seconds; configure `llm.llm_timeout_ms` (1 to 600000 milliseconds) or override it,
for example with `--llm-timeout-ms 240000`. A provider timeout or connection failure logs a warning and skips
that advisory; monitoring continues without an immediate retry or invented advisory.

### Native model artifacts

The native application cannot deserialize Python `.pt` or joblib `.pkl` files. It uses exports of the same
trained detector and Random Forest, without retraining or substituting heuristic risk labels. From
`xWalkPiCarApp/xWalk-pcx86-model`, after training both models, run:

```bash
./xWalkModel export-cpp
```

The model repository provides the exporter and its ONNX dependency. It defaults to input size 640;
`--cpp-imgsz` must match this controller's `model.input_size`. The export validates the detector with OpenCV
DNN and preserves the fitted forest trees. Default files under `model.model_root` are:

- Host and Pi CPU: `xWalkModelResources/xWalkOutput/xWalkNetworkWeights/best.onnx`
- Pi Hailo-8: `xWalkModelResources/xWalkOutput/xWalkNetworkWeights/best.hef`
- Forest: `xWalkModelResources/xWalkOutput/xWalkNetworkWeights/crosswalk-safety.json`

Neither trained source artifacts nor these exports are present in this checkout. Missing, incompatible or
malformed exports fail explicitly. `--weights` and `--rf-model` select explicit export paths. Real-model
agreement and accuracy have not been verified without those artifacts. The ONNX tensor contract and forest JSON
format are documented in [xWalkModel](xWalkModel/xWalkModel.md).

### MQTT announcements

The schema source is `xWalk-rpi5-iw/proto/xHal_Rpi5CarXIwTraffic.proto`; its
`xwalk.traffic.protocol.TrafficObservation` package, field numbers and wire format are preserved. IW's
`cmake/XWalkTrafficProtocol.cmake` generates that schema plus the existing request, common and signal bindings
into `xWalkTrafCtrl/auto-gen` during the CMake build. CMake generates C++ Protobuf bindings only.

The default `mqtt.client_address: "auto"` uses the existing node IPv4 resolver or its `XWALK_SERVER_IP`
override; an explicit IPv4 address is also accepted. `mqtt.server_ip: "0.0.0.0"` broadcasts announcements to
all connected nodes; replace it with a receiver IPv4 address for unicast. `mailbox`, `local_index` and
`module_type` populate both the outer and nested `ClientAddr` records. Set `mqtt.enabled` to `false` for local
evaluation with trace-only announcements.

The publisher reuses `HiveMQClient` and `HiveMQServer`, including verified TLS and existing credential loading.
`XWALK_TRAFCTRL_MQTT_CONFIG_FILE` selects a different connection file before connecting, so a generic
`HIVEMQ_CONFIG_FILE` exported for IoT cannot redirect this process. `XWALK_TRAFCTRL_NETRC_FILE` selects
dedicated credentials; otherwise the normal netrc lookup applies. The environment change is local to the
traffic process. Both presets select this module's `xWalkConfig/xWalkMqttClient.conf` with client ID
`xwalk-traffic-controller`. No credentials are added to traffic JSON.

Advisories use the existing request-topic base plus `/8216` (`CXX_XWALK_CMD_SOUND_REQ`), serialized `SoundReq`
bytes, QoS 1 and no retention. Each carries a unique announcement ID, the `Traffic advisory` title and the
cleaned LLM body. SAFE observations publish no advisory. Broker completion does not confirm playback; the
publisher does not wait for `SoundCfm` or `SoundRej`. Failed or uncertain delivery raises a module error without
an application-level retry. QoS 1 may redeliver the same announcement ID.

### Classified traffic risk display

During host replay, the controller broadcasts the IW `TrafficObservation` once per evaluated frame on
`xwalk/xwalk-pi5-controller/traffic/observation` (QoS 1, non-retained), including SAFE results, before
announcement gating or an LLM call. All GUI clients subscribe to that topic; no device-specific subscription is
used. Live Pi sensor sessions intentionally suppress this periodic feed and send camera-qualified blockage and
clearance advisories instead; with no replay publisher the risk panel remains unknown, which does not mean that
traffic monitoring or the independent sensor stop has failed.

In live mode, Python and Android risk panels use this classifier output instead of local video heuristics;
local detection boxes remain independent and standalone simulation retains its demo display. The panels
display SAFE, WARNING or DANGEROUS plus person and vehicle counts and crosswalk
occupancy. Invalid, incomplete, out-of-range, oversized and retained messages are ignored. After 30 seconds
without valid data, or when the inbox detects a disconnect, the panel shows no current classification. The latest
valid broadcast is displayed when several controllers publish. The IW generator includes this schema for Python
and Java; Android Gradle also generates it directly from the IW checkout.

### Evaluation and announcements

Host mode evaluates a local video offline, by default every 30th decoded frame; `--frame-stride 1` evaluates
every frame. Models load once per session. `--max-frames N` bounds processed frames (zero means EOF or
interrupt). `--evaluation-output FILE` replaces the file and writes one JSONL prediction per processed frame with
source-frame index and timestamp, even when pacing suppresses a repeat; it must not overwrite an input. These are
predictions, not ground-truth accuracy metrics. Decoding failure after readable host frames is treated as EOF.

SAFE observations skip LLM calls. Elevated risk produces an advisory; repeated risk levels are paced by
`announcement_interval` (default 15 seconds) and risk changes are handled immediately. Local host-video
advisories prepend `Simulated incident location: <place>, Halmstad.`, choosing Stora torg, Norre Port, Norre
Katts park, Storgatan or Lilla torg with operating-system randomness. This is a test label, not an inferred
camera or GPS location. Risk advisories from live Pi capture, still images and supplied observation reports
receive no random location; camera-qualified proximity incidents use one simulated location per episode, as
described in [xWalkRuntime](xWalkRuntime/xWalkRuntime.md).
Place names follow the official visitor guide's [Norre Port
page](https://www.destinationhalmstad.se/en/experience/culture-and-history/norre-port-and-halmstad-fortress),
[Norre Katts park
page](https://www.destinationhalmstad.se/en/experience/nature-and-the-outdoor-life/norre-katts-park) and [city
guide](https://www.destinationhalmstad.se/download/18.63702f2818f3e44fa267b14/1715065365940/Upplev_Halmstad_V%C3%A5r_Sommar_2024_LOW2.pdf).

### Host GPU selection

Leave `model.device` as `auto` to select the first usable float32 OpenCV DNN target: CUDA GPU, then OpenCL GPU,
then CPU. Availability requires support in the installed OpenCV build and the runtime driver or device; an
installed GPU alone is not enough, and OpenCL CPU devices are not selected as GPUs. `--device cpu` forces CPU;
`--device cuda` and `--device opencl` fail explicitly if unavailable. A model loading or inference error is not
silently retried. OpenCV may execute unsupported individual layers on CPU. GPU selection changes only the host
detector. See [OpenCV's supported DNN backends and targets](https://docs.opencv.org/4.x/d6/d0f/group__dnn.html).

The regression runs C++ inference on a blank image with the deployment models. It catches importer or
forward-pass incompatibilities; it does not measure accuracy. Real-video evaluation remains necessary. This module
defines no `hardware`-labelled tests; Pi capture, Hailo execution and audible playback have not been run as part of
host verification.

- json-c through pkg-config.

- The Espeak speech provider from [xWalkGPT](../../../02-xwalk-hardware/xWalk-rpi5-hw/xWalkHal/layer1/xWalkGPT/xWalkGPT.md) for

## 10. Safety and constraints

- SAFE is not permission to cross. Generated wording is not guaranteed factual.
- Pi sessions run the independent [front proximity IPC monitor](xWalkProximity/xWalkProximity.md). The hardware
  owner enforces a default 80 mm front-clearance threshold and a latched motor inhibit; traffic inference and
  announcements are never on the stopping path. Sensor safety remains independent of LLM advisory generation.
- Ctrl+C and SIGTERM request exit after the current synchronous capture, inference, LLM or MQTT operation. There
  is no added hard timeout around OpenCV capture or inference.
- Pi capture drops stale frames. Separate processes need separate camera access if both capture
  simultaneously; for concurrent CSI use run [xWalkCameraSvc](xWalkCameraSvc/xWalkCameraSvc.md) and apply its
  shared-camera drop-in to traffic and IoT. Keep one full IoT hardware owner with `--function all`. The
  traffic process does not stop IoT or take over its camera.
- Traffic traces live in this module's build-local `log/`; its Protobuf bindings and configuration are separate
  from IoT. Both applications intentionally receive broadcast advisories where an IoT sound handler runs.
- Responses over 600 bytes or empty responses are rejected and control characters are replaced with spaces.
- Protobuf file input is bounded to 4096 bytes and validated before use. Older observation messages remain
  compatible when the optional normalized geometry fields are absent.
- MQTT broker hostnames, CA bundles and credentials are deployment inputs. Never commit credentials; keep them in
  netrc files selected by the documented environment variables.
